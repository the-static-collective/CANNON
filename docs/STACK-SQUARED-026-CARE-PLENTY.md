## The native care experiment

One fictional meal needs two unavailable ingredient amounts:

- Rice requirement: one cup. The fixture locally declares 0.5 cup available. Nourish evaluates the remaining 0.5 cup and exports that *selected* gap.
- Beans requirement: 0.5 cup. The fixture declares none available, so 0.5 cup remains missing.

Nourish builds the original fulfillment-envelope/v0. Garden holds it locally **twice** but retains **one demand** with two arrival occurrences; reboot reconstruction is exercised in a fresh store instance. Garden builds a per-requirement Campfire POUR preview, but does **not** submit or open any shared need. A circle-labeled preview is not a shared state.

Band Runtime independently receives the exact same original envelope, recognizes repeat carriage, validates two fictional helper events (offer and delivery report), then projects a status packet. A delivery report alone **does not** reduce the rice residual: 0.5 cup remains.

A *separate fabricated recipient-scope event*, clearly marked test-fixture-only, states that 0.25 cup was confirmed. Band projects its source-owned help-case-status/v0 packet; Nourish's source-owned return validator admits the packet as a local **projection**, displaying 0.25 cup rice still missing and 0.5 cup beans missing. The original request/envelope remains byte-identical. This is deliberately a partial outcome.

### Validation and limits

The native refused cases include:
- fabricated claimed-fulfilled source envelope presented to Garden;
- falsified recipient-authorization basis on a Band event;
- mismatched source requirement unit;
- mathematical conservation breach;
- swapped donor source or modified original Git object;
- create-only result overwrite and cold replay tampering.

**Important: Band Runtime validates the *shape and declared basis* of a recipient-authorized event; the fixture does not authenticate an actual recipient.** This proof shows the code's transitions, not real delivery or an independently witnessed occurrence.

No Supabase call, real account, live household, food distribution, money, contact detail, verified service, physical card, or external publication is involved.

## Full Measure deep cut: PLENTY belongs before an offer becomes apparent capacity

Full Measure [PLENTY-001 PR #53](https://github.com/the-static-collective/full-measure-world-layer/pull/53) is a rigorous possibility evaluator. It distinguishes particular → capability → current availability → access → authority → structurally viable paths → independent dependency families. **It does not turn claims into inventory.**

This CANNON experiment calls the exact original Full Measure evaluator with two fictional proposed helper capabilities:
- Both are UNKNOWN: original PLENTY returns POSSIBILITIES_ONLY, zero viable paths.
- One is described as available but UNAUTHORIZED: no viable path.
- Both are *hypothetically* available/authorized but share a single upstream supply: two syntactic viable paths, only **one independent path** (VIABLE_BUT_FRAGILE). Correlation must not become fictional abundance.

This is a separately labeled possibility analysis, NOT a model-generated community resource assignment, and not an adapter by which Band statuses automatically become Full Measure capabilities. Independent authorization and current evidence would be necessary before such a production handoff.

## Run

The GitHub Actions workflow [stack2-026-care-plenty.yml](../.github/workflows/stack2-026-care-plenty.yml) independently checks out the exact original commits, installs only the existing BananaSpork TypeScript runtime dependencies, tests source-byte pins and executes the original code through its tsx runtime.

See [native.mjs](../labs/crater-026/native.mjs) and [native.test.mjs](../labs/crater-026/native.test.mjs). The test must receive absolute paths for four independent Git checkouts in the environment variables CRATER_NOURISH, CRATER_BAND, CRATER_GARDEN, CRATER_PLENTY, and CRATER_TSX_CLI set to the BananaSpork installed tsx CLI. It never searches for a substitute checkout, because a fallback could silently change the proof.

The runner offers create-only run and cold verify, with an inspectable JSON containing source SHA-256 digests, hashed packet references and conservative state labels. It stores no physical participant's information.

**Accept E2 only when the exact PR-head GitHub Actions completes green.** Until then this is a documented candidate, not verified success. Preserve DRAFT / HOLD regardless.
